# Roadmap

| Increment | Scope | Status |
|---|---|---|
| 1 | Foundation, core domain, ledger, API (no UI): reference data, taxonomy, product and criteria language, trade, inventory, registry ports and simulator, allocation engine, position, ledger, workflow, audit, CI, docs | delivered |
| 2 | Registry integrations (outbox, statement formats, Union Registry, API channel), reconciliation break workflow, settlement and invoicing with VAT and netting, counterparty confirmation matching, full approval inbox | delivered (G-REX and NECS mappings wait for their specifications; see the milestone list below) |
| 3 | Valuation and market data (file imports, ECB FX), curves, MtM and P&L explain, period-end accounting, risk limits and credit exposure, ETS compliance (installations, verified emissions, free allocation, surrender), EMIR/MiFID data, reporting, GL interface | delivered (vendor feeds, EMIR layout and SAP layout wait for specifications; see the architecture plan's status) |
| 4 | Web UI (React + TypeScript, bundled in the API jar): approval inbox, trade blotter and capture, inventory explorer with criteria builder, allocation workbench, coverage and expiry dashboards, market data and curves, valuation, risk, ETS compliance, ledger, month end, reports, admin | delivered (out of scope, for a later increment: settlement, invoice and payment screens; registry instructions and breaks; confirmation file matching) |
| 5 | Operations screens: settlement items, invoices, payments, netting and VAT rules; registry instructions and transfer routes; statements and reconciliation breaks; counterparty confirmation matching. Backend first: role and entity guards on these areas, the missing read endpoints and demo data | delivered (statement formats are changed through the API; their editor is left for a later increment) |
| 6 | Scale and operations: observability (Prometheus registry, tracing, JSON logs) and supply chain (SBOM, blocking image scan); Java 25 with virtual threads; Kafka externalisation of events through Spring Modulith; Helm/Kubernetes, HA PostgreSQL; partitioning of version and event tables; exact (CP-SAT) solver; load tests, DR drills, penetration test preparation | delivered (partitioning covers the audit trail and the lot journal; the lot table and version tables stay unpartitioned, see ADR 0030; the penetration test itself is run by an external firm) |
| 7 | Public showcase demo: design system and app shell, showcase login with role personas, six months of demo data in every area with a nightly reset, UI actions for the operations that are API-only today, in-app help manual and guided tours, screenshots, user guide, VPS deployment (Caddy), presentation deck ([plan](plans/increment-7-showcase-demo.md)) | delivered |
| 8 | GoO portfolio management: value-based allocation in EUR with the give-away when specific certificates cover generic sales, shadow prices, available-to-sell, a flow-netted product hierarchy, portfolio value and cheapest-to-deliver (management view), future supply (purchases, expected issuance) that plans reserve against, GoO risk limits ([plan](plans/increment-8-goo-portfolio.md)) | in progress |

Known gaps to close before production: the external penetration test and its retest; a DR drill against a production
backup in the recovery environment; AIB and registry external code lists; sign-off of accounting policies (MtM by
book type, NRV, provision), VAT rules and PFE add-ons; the receiving GL's file specification; market data vendors for
EUA futures and GoO marks; EMIR field layout and trade repository delegation; ETS deadline rules checked by compliance.

## Increment 8: GoO portfolio management

| Milestone | Content | Status |
|---|---|---|
| M0 | Foundations: a compressed flow core (ADR 0036) shared by coverage and headroom. Obligations with identical eligible supply and supply with identical demand merge exactly, so 230 million eligible pairs at 100 000 lots × 5 000 obligations become 21 groups × 12 atoms, solved in 0.1 s. Headroom (sink-blocked augmentation with trial rollback) takes about 1 ms. Eligibility is evaluated once per distinct criterion, date and registry; greedy ranks classes once per score key (237 s → 7 s at design size). The CP-SAT floor is lexicographic on coverage, shortfall and cost. `CriteriaService.implies`; `VintageYears` in the product API; obligations carry their product bucket and vintage; per-entity lot journal sequence | done |
